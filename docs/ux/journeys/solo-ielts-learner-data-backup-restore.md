# User Journey: Backing Up and Restoring Learning Data
Persona: docs/business/personas/solo-ielts-learner.md

## Scenario
The learner is reminded — or reminds themselves — that their entire 180-day study history lives only in this browser with no server-side copy, so they export a full backup; later, a real risk event (a new laptop, a cleared browser, a wipe/reinstall, or simply wanting to prove to themselves the backup actually works) forces them to restore from that file and confirm nothing was lost.

## Steps
| # | Action | Touchpoint | Persona's goal at this step | Risk of drop-off |
|---|---|---|---|---|
| 1 | Notices a "last backup: N days/weeks ago" indicator (or an optional weekly reminder nudge, if the app surfaces one) while on the dashboard | Dashboard / Today Overview — Backup Status indicator | Be reminded of the one risk that a fully client-side, no-server tool creates ("no clear signal... whether things are safe" — pain point: reluctance to trust a tool with no safety net unless they can verify it themselves) | High — this is the core risk of the whole journey: if the indicator is easy to ignore, or no reminder exists yet, the learner simply forgets until a device is already wiped and it's too late |
| 2 | Navigates to the Backup & Restore screen, either from the dashboard prompt or deliberately before doing something risky (e.g. clearing browser data) | Backup & Restore screen | Find the export action quickly, without a guided flow — this is an occasional, deliberate action, not part of the daily study surface, which matches their high technical proficiency and low need for hand-holding | Low — one experienced user, one settings-style screen |
| 3 | Triggers "Export All Data" | Backup & Restore screen — Export action | Get everything (study plan/tasks, vocabulary, mistakes, practice results) into one portable file with a single action, no partial exports to track | Low |
| 4 | Sees confirmation that the export succeeded, with a filename/timestamp, and the browser download completes | Export Confirmation | Get concrete proof the backup exists and is current, updating "last backup" so step 1's indicator resets | Medium — if the confirmation is unclear about where the file went, the learner isn't sure the backup is real, undermining trust in the whole guarantee |
| 5 | Moves the downloaded JSON file to durable storage of their own choosing (cloud drive, USB, another machine) | External storage (outside the app's control — a deliberate scope boundary, not a screen to design) | Keep the backup somewhere that survives the same failure mode it protects against (a wiped or reformatted machine) | Medium — the app can guarantee the export is complete and lossless, but not where the learner keeps the file; a backup left only in the same browser's Downloads folder gives false confidence. Flagged here as a known boundary rather than something this journey's screens can solve. |
| 6 | *(time passes; a real risk event occurs)* — new laptop, cleared browser storage, OS reinstall, or the learner simply decides to verify the backup actually works | *(external trigger, no touchpoint)* | — | — |
| 7 | Opens the app on the now-empty browser and sees a first-run/empty state instead of their usual progress | Dashboard / Today Overview — Empty State | Quickly understand that this is an expected empty state with a known way back, not silent, permanent data loss | High — this is the moment G-5 exists for; if the empty state doesn't immediately surface a restore path, panic ("did I just lose 180 days of progress?") sets in before the learner even reaches step 8 |
| 8 | Navigates to Backup & Restore and selects "Import / Restore" | Backup & Restore screen — Import action | Locate the restore path itself; find it as easily as the export path was found in step 2 | Low-Medium — first time performing this specific action, though high technical proficiency mitigates confusion |
| 9 | Selects the previously exported JSON file from their own storage | Restore File Picker | Point the app at the right backup file with no format guesswork (it's "just a JSON file" they could inspect themselves if needed) | Low |
| 10 | Sees a confirmation warning that restoring will overwrite any existing data, and confirms | Restore Confirmation Dialog (overwrite warning) | Proceed deliberately, trusting that nothing gets destroyed by accident | Medium — genuine hesitation is possible here: if there's any current (even if minimal) data in this browser profile, the fear of making things *worse* by confirming an overwrite could cause the learner to stall or abandon the restore entirely |
| 11 | Data finishes restoring and the app reloads with the full study plan, vocabulary, mistakes, and practice results back in place | Dashboard / Today Overview (post-restore) | See immediate, tangible proof that the restore worked, not just a generic "success" message | Low — once restore completes, relief is immediate if the dashboard clearly reflects the old state |
| 12 | Spot-checks a few areas — vocabulary due count, mistake log entries, progress/analytics — against what they remember, to confirm zero data loss | Vocabulary Due List / Mistake Log / Progress screen (post-restore verification) | Get the concrete, self-verified proof (matching their technical proficiency: "willing to inspect... a JSON backup") that the export→restore round trip lost absolutely nothing | Low — this is the payoff step; the main residual risk is only that they never actually do this check until a real crisis, i.e. skip verifying steps 1-5 ever really worked |

## Emotional Arc
Baseline is low engagement — backup/restore is deliberately not a daily-flow screen, so step 1's reminder needs to catch attention without being annoying. A small flicker of "did that actually work?" uncertainty at the export confirmation (step 4) is resolved quickly since the persona is comfortable verifying things themselves. The arc is flat and dormant through step 5 (file moved to their own storage) until the real risk event (step 6) — the sharpest spike in the whole journey is the moment of seeing an empty dashboard (step 7), where genuine anxiety about permanent loss peaks precisely because this persona chose a no-backend tool for full data ownership and now has to trust that choice was safe. A second, smaller tension point is the overwrite-confirmation dialog (step 10) — a deliberate, not-easily-reversed action. The arc resolves into strong relief and reinforced trust at steps 11-12, when the restored data checks out completely; this is the emotional payoff that retroactively justifies the "no vendor lock-in, full data ownership" trade-off the persona made from the start.

## Success Criteria
- The persona completes a full export (steps 1-4) in well under 2 minutes whenever self-initiated or prompted, without needing to remember file formats, locations, or a multi-step wizard — directly supporting G-5 ("never loses their own learning data").
- At least once, the persona performs a full restore (steps 7-12) after a real or deliberately-simulated data-loss event, and confirms via spot-check (step 12) that the study plan, vocabulary, mistakes, and practice results all came back intact — satisfying the vision metric "a full data export can be re-imported with zero data loss, verified at least once," within a single sitting (well under 10 minutes end-to-end for steps 7-12) and without the overwrite-confirmation step (10) causing the learner to abandon the restore out of fear of losing whatever was already there.

## Candidate Screens
- Dashboard / Today Overview (Backup Status indicator + Empty State variant)
- Backup & Restore screen
- Export Confirmation
- Restore File Picker
- Restore Confirmation Dialog (overwrite warning)
- Post-Restore Verification (dashboard/vocabulary/mistakes/progress views reused, not a new screen)
